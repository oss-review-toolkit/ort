# UI components

This folder holds the **generic, reusable building blocks** of the interface: buttons,
cards, tables, dropdowns, tooltips, and so on. Think of them as the "Lego bricks" the rest
of the app is assembled from.

## Why are they kept separate?

The components in the parent `src/components/` folder are **app-specific** — they know about
ORT concepts like packages, licenses, and vulnerabilities (for example `VulnerabilitiesTable`
or `PackageDetails`). If you deleted this project, those components would make no sense
elsewhere.

The components in *this* folder are the opposite: they are **generic** and know nothing about
ORT. A `Button` is just a button; a `Card` is just a card. You could copy them into a
completely different app and they would still work. Keeping them in their own folder makes
that distinction obvious at a glance:

| Folder                | What lives here                                            |
| --------------------- | ---------------------------------------------------------- |
| `src/components/`      | Components that understand ORT data (the actual report UI) |
| `src/components/ui/`   | Generic UI bricks that any app could use                   |

## Where do they come from?

These files are generated by [shadcn/ui](https://ui.shadcn.com), a tool that copies
ready-made component source directly into the project. Because the code lives here (rather
than in an installed package), we own it and can edit it — but in practice you rarely need to.
New primitives are usually added with the shadcn CLI, for example:

```sh
npx shadcn@latest add button
```

The tool always places components in this `ui/` folder — that path is configured in
`components.json` at the project root. That is another reason to leave the folder named `ui/`
and not move these files elsewhere.

## `data-table/`

The `data-table/` subfolder is a small, self-contained module that builds a full-featured,
sortable/filterable/paginated table on top of these primitives. It is also generic (it knows
nothing about ORT), which is why it belongs here alongside the other reusable bricks rather
than next to the app-specific components. Import it as a unit:

```ts
import { DataTable, DataTableColumnHeader } from "@/components/ui/data-table";
```

## Filename convention

Files that define a component use `PascalCase` (`Button.tsx`, `DropdownMenu.tsx`) to match the
rest of the codebase. Plain helper files that do not export a component stay lowercase
(for example `data-table/expandedRow.ts`).
